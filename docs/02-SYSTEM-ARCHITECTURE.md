## 2. Purpose

The purpose of this architecture is to transform Forge Wanzz from an abstract concept into an implementable, robust, and sovereign **AI Software Factory**. 

Traditional agentic tooling suffers from critical structural flaws:
1. **Conflated Responsibilities:** LLMs act simultaneously as planners, state stores, runners, and judges.
2. **Hallucinated State:** Task progress exists solely in chat context windows rather than authoritative databases.
3. **Pseudoscience Security:** Systems make unprovable claims of "complete sandboxing" over opaque external processes.
4. **Self-Attested Verification:** Agents declare their own work "complete" without deterministic verification.
5. **Brittle Recovery:** Process crashes lead to corrupted workspaces, orphan child processes, and permanent task death.

Forge Wanzz resolves these pathologies through a **modular, local-first, contract-driven architecture** characterized by deterministic control planes, strict single-owner state domains, explicit runtime trust boundaries, and dual-layer verification.

## 3. Architectural Principles

The Forge Wanzz architecture is governed by eight immutable engineering principles:

1. **Deterministic Control over Probabilistic Reasoning:** LLM inference is stochastic; system coordination, task state machines, capability authorization, and verification gates are 100% deterministic. An agent cannot declare itself finished; it must prove correctness through authoritative evidence (*"Agent: Done. Forge: Prove it."*).
2. **Strict Separation of Coordination and State:** The planning brain does not own task state. The Orchestrator plans, decomposes, and proposes; the Task Engine validates, transitions, and persists.
3. **Local-First Engineering Reality:** Forge V0.1 operates as a sovereign local development control plane. It is implemented as a Modular Monolith with clean internal service interfaces, process isolation, and an embedded SQLite database using Write-Ahead Logging (WAL). Unnecessary distributed complexity (Kubernetes, Kafka, microservices, Raft) is strictly prohibited.
4. **Single Authoritative Ownership:** Every state domain (tasks, agents, executions, organizations, verification evidence) is owned by exactly one subsystem. No dual-write paths exist.
5. **Security Honesty & Explicit Boundaries:** Forge distinguishes between fully governed native runtimes and opaque external CLI processes. It enforces security at the boundary of execution and workspace rather than pretending to inspect internal CLI sub-tokens.
6. **Capability Resolution Prior to Execution:** Possession of a skill or tool definition does not grant authorization. Execution requires a cryptographically validated `ExecutionToken` generated by an independent Capability Resolver.
7. **Durable Leases and Crash Resilience:** All active executions require time-bounded, heartbeat-monitored leases. On restart, the system cleanly sweeps orphan processes, reconciles leases, and validates workspace integrity before resuming.
8. **Asynchronous Decoupling via Commands and Events:** Subsystems interact via strongly-typed mutation commands directed to authoritative owners and subscribe to immutable domain events emitted after successful state changes.

### 5.1 Distinction Matrix

To prevent architectural collapse, the following distinctions are enforced across all layers:

- **Agent ≠ Model:** An Agent is an identity with a role (e.g., "Senior Backend Engineer"); a Model is an inference engine (e.g., `claude-3-5-sonnet`, `deepseek-coder`). One agent can switch models across its lifecycle.
- **Agent ≠ Runtime:** An Agent holds context and goals; a Runtime is the execution host (e.g., Node.js subprocess, Docker container, external CLI) where code actually executes.
- **Runtime ≠ Provider:** A Runtime executes commands and tools; a Provider streams tokens and inference responses.
- **Skill ≠ Tool:** A Skill is procedural knowledge ("How to refactor a React component to TypeScript"); a Tool is an executable primitive (`write_file`, `git_commit`, `execute_command`). Skills guide tool selection; skills never execute tools directly.
- **Orchestrator ≠ Task Engine:** The Orchestrator creates planning proposals; the Task Engine is the stateful database authority for tasks and dependencies.

## 7. Architectural Layers

### 7.1 Layer 1: Interface Layer

The Interface Layer provides sovereign human control and observability into the factory. It translates human instructions into system intents and renders factory state in real time.

- **CLI (`forge-cli`):** The primary command-line tool for developers. Supports headless script execution, daemon launching, interactive planning, and project initialization (`forge init`, `forge plan`, `forge run`, `forge status`).
- **Web Dashboard (`forge-dashboard`):** Modern local web UI providing visual DAG exploration, agent activity monitoring, terminal streaming, diff inspection, and interactive human approval prompts.
- **Human Operator Interface (Gateway):** Unified input adapter exposing typed RPC and Server-Sent Events (SSE) / WebSocket endpoints for real-time bidirectional telemetry between UI clients and the Control Plane.

### 7.2 Layer 2: Control Plane

The Control Plane is the deterministic operating system of Forge Wanzz. It orchestrates the lifecycle of projects, plans, teams, tasks, capabilities, and verification gates.

- **Project Manager:** Authoritative owner of project configurations, root workspaces, lifecycle stages, and persistence boundaries.
- **Goal / Intent Gateway:** Ingests unstructured human goals, performs lexical and constraint parsing, and registers validated goals.
- **Organization Manager:** Authoritative manager of AI organization topologies, team structures, role declarations, and concurrency quotas.
- **Orchestration Engine:** Strategic planner that breaks goals down into task graph proposals and coordinates multi-agent workflows.
- **Task Engine:** The sole authoritative owner of task state, DAG relationships, dependency resolution, task queues, and execution leases.
- **Capability Resolver:** Centralized security authority that resolves effective permissions across task, agent, skill, tool, and policy definitions, issuing cryptographic `ExecutionTokens`.
- **Approval Manager:** Manages human-in-the-loop (HITL) authorization gates, pause states, and escalation requests.
- **Verification Engine:** Deterministic evaluation authority executing builds, tests, linters, and compilers to validate task outcomes.
- **Policy / Security Authority:** Authoritative evaluator of workspace security rules, network access boundaries, and credential safety.
- **Event System:** Central typed messaging backbone supporting synchronous internal commands and asynchronous domain events.

### 7.3 Layer 3: Intelligence / Agent Layer

The Intelligence Layer manages autonomous decision-making agents as governed entities.

- **Agent Engine:** Manages agent execution identities, persona configurations, working memory buffers, and agent lifecycles.
- **Agent Context Manager:** Compiles task context, constraints, and relevant file summaries into optimized LLM prompt budgets.
- **Skill Engine (Registry):** Hosts reusable procedural knowledge manifests using two-tier progressive disclosure.
- **Reviewer Agents:** Specialized agent personas operating exclusively as Layer 2 semantic auditors (code style, architectural coherence, test adequacy).

### 7.4 Layer 4: Execution Layer

The Execution Layer provides physical isolation, process management, tool execution, and runtime adaptation.

- **Runtime Engine:** Manages execution host discovery, health monitoring, process allocation, and runtime abstraction.
- **Runtime Router & Adapters:** Routes execution requests to appropriate runtime adapters:
  - *L4 Native Adapter:* Direct in-process or local child process with full tool interception.
  - *L3 Sandboxed Adapter:* Containerized environment (Docker/Podman) with strict filesystem and network isolation.
  - *L1 External CLI Adapter:* Process boundary adapter for third-party CLIs (Claude Code, OpenCode).
- **Provider Router:** Multiplexes LLM inference requests across upstream providers (Anthropic, OpenAI, local Ollama) with fallback and rate limiting.
- **Tool Execution Engine:** Deterministic executor of discrete tool actions (`read_file`, `write_file`, `exec_command`, `git_commit`) governed by capability tokens.
- **Workspace Manager:** Isolates concurrent agent file mutations using dedicated Git Worktrees.
- **Process Manager:** Tracks OS process trees using Process Group IDs (`pgid`) to guarantee zero orphan processes on cancellation or crash.

### 7.5 Layer 5: State / Data Layer

The State Layer provides atomic, crash-resilient persistence for all factory operations.

- **SQLite Core Engine:** Single embedded database operated in Write-Ahead Logging (WAL) mode with `busy_timeout = 5000ms`.
- **Domain Tables:** Strict relational schema partitions state across domain boundaries.
- **Artifact Store:** Filesystem-backed storage for diff patches, test logs, execution evidence, and build binaries.
- **Memory Store:** SQLite relational context plus embedded vector index (sqlite-vec / sqlite-vss) for semantic retrieval.

### 10.1 Authority Invariants
- No component may bypass the Capability Resolver to execute tools or commands.
- The Orchestrator has **zero** authority to mutate the `tasks` table. It must issue a `ProposeTaskGraph` command to the Task Engine.
- The Agent Engine has **zero** authority to spawn agents without an organizational allocation approved by the Organization Manager.
- A Reviewer Agent has **zero** authority to pass a task if the Verification Engine recorded a deterministic failure (e.g., failed tests or compile errors).

## 12. Command / Event Model

Forge Wanzz strictly bifurcates subsystem communication into **Commands** and **Events**:

```text
+------------------------------------------------------------------------------------------------+
| COMMAND (Imperative Request)                                                                   |
| - Directed to a specific owning subsystem.                                                     |
| - Can be validated, accepted, or rejected.                                                     |
| - May trigger state mutations within the recipient domain.                                     |
| - Example: Orchestrator -> ProposeTaskGraphCommand -> Task Engine                              |
+------------------------------------------------------------------------------------------------+
                                              │
                                              ▼ (State Mutation in SQLite)
+------------------------------------------------------------------------------------------------+
| EVENT (Immutable Past-Tense Fact)                                                              |
| - Emitted to the Event Bus after a state mutation successfully commits to SQLite.              |
| - Cannot fail, cannot be rejected, and contains an immutable payload.                          |
| - Subscribed to by interested subsystems for cache updates, telemetry, or scheduling triggers. |
| - Example: Task Engine -> TaskReadyEvent -> Orchestrator                                       |
+------------------------------------------------------------------------------------------------+
```

### 12.1 Communication Protocols
- **In-Process Dispatch:** In V0.1, commands and events are executed via a strongly-typed TypeScript EventEmitter / Dispatcher pattern.
- **Transactional Discipline:** A domain event is **never** emitted until the underlying database transaction has successfully committed (`commit()`).
- **Zero Event Mutation:** Subsystems receiving events are strictly forbidden from mutating another subsystem's state directly in response. If an event triggers follow-up action, the subscriber must issue a new typed **Command** to the target owner.

## 14. Planning & Task Flow

The relationship between the Orchestration Engine and the Task Engine represents the core constitutional boundary of Forge Wanzz.

```text
+---------------------------------------------------------------------------------------+
|                              ORCHESTRATOR / TASK ENGINE BOUNDARY                      |
+---------------------------------------------------------------------------------------+
|                                                                                       |
|   +--------------------------+                         +--------------------------+   |
|   |   ORCHESTRATION ENGINE   |                         |       TASK ENGINE        |   |
|   |                          |                         |                          |   |
|   | - Strategic Planning     |                         | - State Authority        |   |
|   | - Goal Decomposition     |   1. ProposeTaskGraph   | - DAG Cycle Detection    |   |
|   | - Agent Role Matching    |────────────────────────►| - Dependency Evaluation  |   |
|   | - Dynamic Replanning     |                         | - Lease Management       |   |
|   | - Human Escalation       |   2. Proposal Accepted  | - Transition Validation  |   |
|   |                          |◄────────────────────────| - Task Queue Scheduling  |   |
|   +--------------------------+                         +--------------------------+   |
|                ▲                                                     │                |
|                │                                                     │                |
|                │              3. TaskReadyEvent                      │                |
|                └─────────────────────────────────────────────────────┘                |
|                                                                                       |
+---------------------------------------------------------------------------------------+
```

### 14.1 The Proposal-Validation Cycle
1. **Decomposition:** The Orchestrator generates a `TaskGraphProposal` containing proposed task nodes, assigned agent roles, input context, expected artifact contracts, and dependency edges.
2. **Structural Validation:** The Task Engine inspects the proposal for:
   - Graph topology validity (directed acyclic graph check; zero cycles permitted).
   - Task definition schemas (valid names, role mappings, execution timeouts).
   - Duplicate idempotency keys.
3. **Atomic Persistence:** Upon successful validation, the Task Engine persists the tasks and edges into SQLite within a single transaction.
4. **State Machine Initiation:** Tasks with zero unsatisfied dependencies are transitioned to `READY`. The Task Engine emits `TaskReadyEvent`.
5. **No Backdoor Mutation:** The Orchestrator cannot mark a task `RUNNING`, `COMPLETED`, or `FAILED`. State mutations are exclusively performed by the Task Engine based on execution and verification results.

## 19. Workspace & Isolation Model

Concurrent file modifications without isolation produce race conditions, git index corruption, and merge collisions. Forge Wanzz enforces workspace isolation based on access patterns:

```text
+---------------------+-------------------------------+-------------------------------------------+
| Access Pattern      | Workspace Topology            | Isolation Mechanism                       |
+---------------------+-------------------------------+-------------------------------------------+
| READ-ONLY           | Shared Canonical Workspace    | Direct read access allowed.               |
| SINGLE WRITER       | Direct or Isolated Branch     | Git branch in isolated path recommended.  |
| CONCURRENT WRITERS  | Isolated Git Worktrees        | MANDATORY Git Worktree per active task.   |
+---------------------+-------------------------------+-------------------------------------------+
```

### 19.1 Git Worktree Isolation Architecture

```text
Canonical Git Repository Root (/project)
   │
   ├── .git/
   ├── src/
   │
   └── .forge/worktrees/
           │
           ├── worktree_task_A/   (Branch: forge/task-A) [Agent 1: Backend API]
           │     └── Isolated file edits & test executions
           │
           └── worktree_task_B/   (Branch: forge/task-B) [Agent 2: Frontend UI]
                 └── Isolated file edits & test executions
```

### 19.2 The Worktree Lifecycle
1. **Creation:** When a write-capable task enters `SCHEDULED`, Workspace Manager executes:  
   `git worktree add -b forge/tsk_<id> .forge/worktrees/tsk_<id> HEAD`.
2. **Execution:** The agent and tools are strictly confined to this directory via path checks in the `ExecutionToken`.
3. **Diff Verification:** Verification tests run inside this isolated worktree.
4. **Integration Pipeline:** Upon task verification success, the branch is merged into the integration branch via a serialized git merge pipeline. Merge conflicts trigger human escalation or a specialized conflict-resolution task.
5. **Pruning:** After merge, the worktree is cleanly removed: `git worktree remove --force .forge/worktrees/tsk_<id>`.

## 20. Verification Architecture

Verification in Forge Wanzz is strictly **dual-layered**. An agent saying *"I have completed the task"* has **zero** evidentiary value.

```text

                                            │
                                            ▼
                    =================================================
                    LAYER 1: VERIFICATION ENGINE (Deterministic)
                    =================================================
                    - Compiler / Type Checker (tsc, rustc, go build)
                    - Linter & Style Rules (eslint, ruff, clippy)
                    - Unit & Integration Test Suites (pytest, jest)
                    - Build Artifact Validation
                    - Git Diff & Scope Boundary Checks
                    =================================================
                                            │
                                   Deterministic Proof?
                                            │
                             ┌──────────────┴──────────────┐
                             ▼                             ▼
                          [ FAIL ]                      [ PASS ]
                             │                             │
                      Task Marked FAILED                   ▼
                     Evidence Recorded in DB      ===================================
                     Agent Re-attempts or         LAYER 2: REVIEWER AGENT (Semantic)
                     Orchestrator Replans         ===================================
                                                  - Architectural Integrity Review
                                                  - Maintainability & Readability

                                                  ===================================
                                                                   │
                                                            Semantic Pass?
                                                                   │
                                                    ┌──────────────┴──────────────┐
                                                    ▼                             ▼

                                                    │                             │
```

### 20.1 Verification Invariants
- **Layer 1 is Authoritative:** If Layer 1 fails (non-zero exit code, test failure, compiler error), the task is marked `FAILED`. No agent or LLM can override a Layer 1 failure.
- **Layer 2 is Advisory/Qualitative:** Layer 2 can reject code that passed Layer 1 if it violates architectural invariants or security patterns. Layer 2 cannot approve code that failed Layer 1.
- **Evidence Storage:** All test outputs, compiler logs, and review summaries are persisted in the `verification_reports` table as permanent audit records.

### 22.1 Enforceable Security Guarantees vs Non-Guarantees
- **What Forge Enforces:**
  - Strict filesystem path boundary checks for native tools.

  - OS-level process group tracking and complete process termination.
  - Ephemeral Git Worktree isolation for all write operations.

- **What Forge Does NOT Falsely Claim:**
  - Forge does **not** claim to inspect internal sub-process tool calls executed within opaque external CLIs (Claude Code, OpenCode).
  - External CLIs are governed at the **process boundary** (restricted working directory, process group timeouts, post-execution diff verification) and **not** by pretending MCP is an airtight internal sandbox.

## 23. Runtime Trust Model

Forge Wanzz classifies all execution runtimes into a **5-Class Runtime Trust Model**:

```text
+-----------------------------------------------------------------------------------------------+
| Class | Designation      | Description                 | Governance & Interception Mechanisms |
+-------+------------------+-----------------------------+--------------------------------------+
| L0    | UNKNOWN          | Unverified binary / script. | Blocked by default. Manual override. |
| L1    | TRUSTED EXTERNAL | Opaque external AI CLI      | Process boundary governance only.    |
|       |                  | (Claude Code, OpenCode).    | Monitored via Git Worktree diffs.    |
| L2    | GOVERNED         | CLI or agent with MCP tool  | Tool-level interception via MCP proxy.|
|       |                  | proxy interception.         | Process-level resource constraints.  |
| L3    | SANDBOXED        | Containerized environment   | OS-level filesystem & network jail.  |
|       |                  | (Docker / Podman / Chroot). | Full isolation from host system.     |
| L4    | NATIVE FORGE     | Internal TypeScript/Node    | 100% fine-grained token verification.|
|       |                  | execution environment.      | In-process parameter validation.     |
+-------+------------------+-----------------------------+--------------------------------------+
```

### 23.1 Trust Class vs Capability Profile
Trust Class describes **how execution is isolated and monitored**; Capability Profile describes **what the agent is authorized to do**. An L1 runtime may be authorized to write code, but Forge treats its internal operation as an uninspected black box, verifying only the output diffs. An L4 runtime has every individual tool call intercepted, authorized, and logged.

## 25. Crash Recovery

The Crash Recovery subsystem ensures that Forge Wanzz can be abruptly terminated (`kill -9`, power outage, machine restart) and recover cleanly without corrupting task state or leaking zombie processes.

```text
                                  [ SYSTEM STARTUP ]
                                          │
                                          ▼
                            [ 1. DATABASE RECOVERY ]
                            - Open SQLite in WAL mode
                            - Check database integrity (`PRAGMA integrity_check`)
                                          │
                                          ▼
                         [ 2. ORPHAN PROCESS SWEEP ]
                         - Query `executions` where status = 'RUNNING'
                         - Read stored `process_group_id` (`pgid`)
                         - Send `SIGTERM` / `SIGKILL` to entire process groups
                                          │
                                          ▼
                         [ 3. LEASE EXPIRATION RECONCILIATION ]
                         - Find active `task_leases` where:
                           `last_heartbeat_at` < (NOW - lease_timeout)
                         - Revoke stale leases
                                          │
                                          ▼
                         [ 4. WORKSPACE INTEGRITY VALIDATION ]
                         - Inspect all `.forge/worktrees/` directories
                         - Check git status for uncommitted / dirty files
                         - If corrupted: wipe worktree, re-create from HEAD
                                          │
                                          ▼
                         [ 5. TASK RESUMPTION EVALUATION ]
                         - If execution was idempotent and clean: mark `READY`
                         - If execution left unverified state: mark `FAILED_RECOVERY`
                         - Notify Orchestrator / Human Operator
```

### 25.1 Durable Lease Protocol
- Every active execution acquires a lease in the `task_leases` table.
- **Lease Duration:** 30 seconds default.
- **Heartbeat Interval:** Active runtimes must write a heartbeat every 5 seconds.
- If a heartbeat is missed for >30 seconds, the Task Engine considers the lease expired and reclaims the task.

## 27. State Machine Relationships

Forge Wanzz manages seven interconnected state machines with strictly defined cascade rules:

```text
===================================================================================
1. GOAL STATE MACHINE
   [ SUBMITTED ] ──► [ PLANNING ] ──► [ EXECUTING ] ──► [ VERIFYING ] ──► [ FULFILLED ]
                                             │                                ▲
                                             └──► [ FAILED ] ─────────────────┘

2. PLAN STATE MACHINE
   [ DRAFTING ] ──► [ PROPOSED ] ──► [ ACCEPTED ] ──► [ SUPERSEDED / COMPLETED ]
                           │
                           └──► [ REJECTED ]

3. TASK STATE MACHINE (Owned Exclusively by Task Engine)
   [ PENDING ] ──► [ READY ] ──► [ SCHEDULED ] ──► [ RUNNING ] ──► [ VERIFYING ] ──► [ COMPLETED ]
          │                                             │               │
          └──► [ BLOCKED ]                              └──► [ PAUSED ] └──► [ FAILED ]
          │                                                     │               │
          └─────────────────────► [ CANCELLED ] ◄───────────────┴───────────────┘

4. EXECUTION LEASE STATE MACHINE (Owned by Runtime Engine)
   [ ACQUIRING ] ──► [ ACTIVE_HEARTBEATING ] ──► [ RELEASED ]
                            │
                            └──► [ EXPIRED / REVOKED ]

5. VERIFICATION STATE MACHINE (Owned by Verification Engine)
   [ QUEUED ] ──► [ RUNNING_LAYER1 ] ──► [ RUNNING_LAYER2 ] ──► [ PASSED ]
                         │                      │
                         └──────────────────────┴─────────────► [ FAILED ]

6. APPROVAL STATE MACHINE (Owned by Approval Manager)
   [ NOT_REQUIRED ] / [ PENDING ] ──► [ APPROVED ]
                             │
                             └──► [ REJECTED ] / [ EXPIRED ]
===================================================================================
```

### 27.1 Cascade Rules
- When a Goal transitions to `CANCELLED`, the Task Engine marks all non-terminal tasks (`PENDING`, `READY`, `SCHEDULED`, `RUNNING`) as `CANCELLED`.
- When a task enters `RUNNING`, an Execution Lease must transition to `ACTIVE_HEARTBEATING`.
- When a task fails Layer 1 verification, it **cannot** enter `COMPLETED`; it transitions to `FAILED`.

```text
       │
       ├── 1. PAUSE / RESUME      --> Temporarily halts task dispatch without killing state.
       ├── 2. ABORT GOAL          --> Sends SIGKILL to active execution pgids; cancels all tasks.
       ├── 3. FORCE VERIFY        --> Manually triggers or overrides Layer 2 review (NOT Layer 1).
       ├── 4. ROLLBACK WORKTREE   --> Discards dirty worktree and restores branch from HEAD.
       └── 5. INTERACTIVE APPROVE --> Explicitly grants or denies escalated capability requests.
```

All human interventions are signed into the `security_audit_log` with an immutable operator timestamp.

## 34. Architectural Invariants

The following twelve architectural invariants are **binding and non-negotiable** across the entire Forge Wanzz project:

1. **INVARIANT-001 (Single Authoritative Owner):** Every persistent state domain has exactly one authoritative owning subsystem. No dual-write paths are permitted.
2. **INVARIANT-002 (Orchestrator Proposes, Task Engine Decides):** The Orchestrator plans and proposes task graph mutations; the Task Engine validates, transitions, and persists task state. The Orchestrator shall never mutate the `tasks` table directly.
3. **INVARIANT-003 (Organizational Sovereignty):** The Organization Manager owns AI team formation, roles, and quotas. The Orchestrator requests roles; the Agent Engine provisions execution identities. Arbitrary agent spawning is prohibited.
4. **INVARIANT-004 (Dual-Layer Verification Authority):** Deterministic verification (Layer 1) is authoritative. Probabilistic semantic review (Layer 2) is advisory. An agent's self-attestation of completion has zero authority. No agent can override a Layer 1 failure.
5. **INVARIANT-005 (Capability Precedes Execution):** Skill declarations or tool definitions do not grant permission. Execution requires a valid, time-bounded `ExecutionToken` issued by the Capability Resolver.
6. **INVARIANT-006 (Runtime Trust Realism):** Forge shall not falsely claim complete governance over opaque external CLIs. Trust classes must explicitly represent the boundary between native interception and process-level confinement.
7. **INVARIANT-007 (Concurrent Workspace Isolation):** Concurrent writing agents shall never operate on the same shared directory. Multiple concurrent writers must be isolated via dedicated Git Worktrees.
8. **INVARIANT-008 (Crash Integrity Precedes Resumption):** On restart, the system must validate database integrity, sweep orphan process groups, and reconcile dirty worktree states before resuming tasks.
9. **INVARIANT-009 (Entity Independence):** The distinctions between Model, Provider, Runtime, Agent, Skill, Tool, Task, Orchestrator, and Factory must be preserved across all specifications.
10. **INVARIANT-010 (Command / Event Bifurcation):** Mutations occur via directed typed commands to owning subsystems. Domain events are immutable facts emitted post-commit. Events shall never be used as backdoor mutation channels.
11. **INVARIANT-011 (Local-First Simplicity):** The core engine must operate locally with zero cloud dependencies, external message brokers, or distributed orchestrators.
12. **INVARIANT-012 (Auditable Human Sovereignty):** Human operators retain ultimate authority to pause, cancel, approve, or rollback any factory operation. All human interventions must be logged to the security audit trail.
