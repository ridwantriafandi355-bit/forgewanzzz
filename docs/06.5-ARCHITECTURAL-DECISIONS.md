## AD-001 — Task Graph Ownership

### Status
**LOCKED**

### Context
Documents `05-ORCHESTRATION-ENGINE.md` and `06-TASK-ENGINE.md` exhibited a fatal structural overlap: both engines claimed ownership of task state, dependency resolution, graph mutation, and execution lifecycle.

### Problem
When both the coordination layer (Orchestrator) and the state layer (Task Engine) have direct mutation authority over the Task Directed Acyclic Graph (DAG), distributed state corruption, race conditions during parallel execution, and split-brain recovery after process restarts are mathematically inevitable.

### Options Considered
- **Option A (Orchestrator-Centric):** Orchestrator holds the in-memory Task DAG, mutates states directly, and periodically snapshots to an external key-value or document store.
- **Option B (Task Engine Authority — CHOSEN):** Task Engine is the sole authoritative state machine and ACID persistence owner of the Task DAG. The Orchestrator acts purely as a stateless planner and scheduling intelligence issuing commands/requests.
- **Option C (Shared Memory / Actor Model):** Tasks are standalone stateful actors communicating via asynchronous message channels.

### Decision
**The Task Engine is the sole authoritative owner of the Task Graph and Task State.**  
The Orchestrator determines *what should happen* (planning, decomposition strategy, scheduling proposals, agent assignment proposals, replanning algorithms). The Task Engine records *what is true* (task definitions, state transitions, dependency satisfaction, DAG acyclic validation, lease tracking, persistent state recovery). The Orchestrator MUST NOT mutate task state directly; it issues command intents to the Task Engine.

### Authority
**Task Engine (`@forge/task-engine`)**

### Responsibilities
- **Task Engine MUST:**
  - Persist task definitions, dependencies, and state transitions to ACID storage.
  - Validate that state transitions follow the canonical Task State Machine.
  - Perform DAG cycle detection before accepting task graph mutations.
  - Evaluate dependency satisfaction and transition tasks to `READY`.
  - Enforce lease locks and detect stalled/abandoned tasks.
- **Orchestrator MUST NOT:**
  - Write directly to the task storage tables or mutate task objects in memory.
  - Declare a task `COMPLETED` or `FAILED` independently of the Task Engine.
  - Maintain an un-synchronized shadow task graph.

### Contract
```text
Orchestrator                          Task Engine
     │                                     │
     │── 1. ProposeTaskGraph(tasks, edges)─►│
     │                                     │ (Validates DAG & Persists)
     │◄── 2. GraphAccepted(graph_id)───────│
     │                                     │
     │◄── 3. TaskReadyEvent(task_id)───────│ (Dependencies Satisfied)
     │                                     │
     │── 4. DispatchTask(task_id, agent)───►│
     │                                     │ (Transitions to RUNNING)
     │◄── 5. LeaseGranted(execution_id)────│
```

### Invariants
- `INVARIANT-001.1`: There is exactly one authoritative state machine for tasks: the Task Engine.
- `INVARIANT-001.2`: The Orchestrator proposes; the Task Engine validates and records.

### Consequences
- **Positive:** Immune to race conditions during parallel execution; deterministic crash recovery; Orchestrator can restart without losing task states.
- **Negative:** Minor IPC / function call overhead between Orchestrator and Task Engine; Orchestrator must handle rejected state transitions.

### Rejected Alternatives
- Option A was rejected because an in-memory graph held by the Orchestrator causes total loss of task state if the Orchestrator crashes during step execution.
- Option C was rejected as over-engineered for MVP local runtime execution.

### Affected Documents
- `05-ORCHESTRATION-ENGINE.md`: Strip direct state mutation methods (`create_task`, `complete_task`, etc.).
- `06-TASK-ENGINE.md`: Full rewrite establishing the definitive Task DAG persistence, lease, and transition engine.
- `16-DATABASE-SCHEMA.md`: Ensure schema models tasks, dependencies, and execution leases under Task Engine ownership.

### Implementation Notes
The Task Engine must implement a clean service interface (`TaskService.proposeGraph()`, `TaskService.transitionState()`, `TaskService.acquireLease()`) backed by atomic SQLite transactions in WAL mode.

## AD-002 — Organization Ownership

### Status
**LOCKED**

### Context
`01-MASTER-PRD.md` and `02-SYSTEM-ARCHITECTURE.md` established the concept of an dynamic "AI Organization", but `05-ORCHESTRATION-ENGINE.md` claimed the authority to spawn and form organizations, creating role overlap with the `Organization Manager` and `Agent Engine`.

### Problem
If the Orchestrator directly instantiates and manages agents, the distinction between coordination (workflow) and resource allocation (identity and persona governance) collapses, preventing centralized governance of agent quotas, roles, and security bounds.

### Options Considered
- **Option A (Orchestrator Spawns Agents):** Orchestrator analyzes the project and dynamically instantiates arbitrary agent processes directly.
- **Option B (Dedicated Organization Manager — CHOSEN):** Orchestrator defines required capability roles; Organization Manager provisions and structures the team; Agent Engine instantiates and manages agent execution identities.
- **Option C (Static Pre-Configured Teams):** Users manually configure all agents in `.forge/agents.yaml`; no dynamic formation.

### Decision
**The Organization Manager is the sole authority for assembling, structuring, and governing the AI Organization.**  
The Orchestrator identifies and requests the *capabilities and roles* required by a project plan. The Organization Manager evaluates project policies, budgets, and team templates to form the organization. The Agent Engine instantiates and manages the individual agents within that organization.

### Authority
**Organization Manager (`@forge/org-manager`)**

### Responsibilities
- **Orchestrator:** Formulates capability requirements (e.g., "Requires Frontend React Specialist, PostgreSQL DBA, and Test Engineer").
- **Organization Manager:** Resolves requirements against project constraints, enforces maximum agent limits, defines reporting hierarchy, and provisions the team.
- **Agent Engine:** Owns agent identity, system prompts, active skills binding, and working memory.

### Contract
```text
Orchestrator               Organization Manager              Agent Engine
     │                               │                             │
     │── 1. RequestTeam(roles)──────►│                             │
     │                               │── 2. ProvisionAgent(spec)──►│
     │                               │◄── 3. AgentReady(agent_id)──│
     │◄── 4. TeamAssembled(org_id)───│                             │
```

### Invariants
- `INVARIANT-002.1`: The Orchestrator coordinates work among existing agents; it cannot create agents unilaterally.
- `INVARIANT-002.2`: Every agent belongs to exactly one Organization within a Project.

### Consequences
- **Positive:** Centralized policy enforcement; prevents infinite agent spawning loops; clear audit trail of organizational structure.
- **Negative:** Introduces an intermediate management component between high-level planning and individual agent execution.

### Rejected Alternatives
- Option A was rejected because allowing the LLM-driven Orchestrator to spawn arbitrary agents invites runaway token consumption and ungoverned system processes.
- Option C was rejected as too rigid for an autonomous software factory.

### Affected Documents
- `02-SYSTEM-ARCHITECTURE.md`: Complete Section 5 to formally define `Organization Manager`.
- `03-AGENT-SYSTEM.md`: Clarify that agent provisioning requests originate from Organization Manager.
- `05-ORCHESTRATION-ENGINE.md`: Remove agent instantiation logic; replace with team requirement requests.

### Implementation Notes
The Organization Manager maintains an organizational manifest associating `project_id`, `organization_id`, and active `agent_ids`.

## AD-003 — Runtime Trust Model

### Status
**LOCKED**

### Context
Forge Wanzz bridges local developer tools and autonomous execution. Claiming that external AI coding CLIs (e.g., Claude Code, OpenCode) are "100% sandboxed and governed" when Forge merely spawns them as subprocesses is factually false and introduces grave security vulnerabilities.

### Problem
Different execution environments provide vastly different security, isolation, and observability capabilities. Treating an un-sandboxed third-party CLI identically to an isolated WebAssembly sandbox creates false security assumptions.

### Options Considered
- **Option A (Binary Trust: Trusted vs Untrusted):** Simple flag on runtimes.
- **Option B (Tiered Trust Matrix — CHOSEN):** Explicit multi-level runtime trust model (`L0` through `L4`) with programmatic capability and security disclosures.
- **Option C (Enforce Total Sandboxing Only):** Refuse to support any runtime that cannot be placed inside a strict Docker/gVisor sandbox.

### Decision
**Forge adopts a 5-Tier Runtime Trust Model (L0 to L4). Forge MUST expose the exact technical guarantees available for each runtime and never claim governance over un-intercepted external processes.**

```text
[L0: UNKNOWN]
  └── Completely unverified binary; zero isolation; blocked by default.
[L1: TRUSTED EXTERNAL]
  └── Standard CLI (Claude Code, OpenCode, Codex); host OS privileges;
      tool interception is NOT guaranteed; relies on user's local trust.
[L2: GOVERNED]
  └── Process monitored via PTY/IPC hooks; filesystem restricted by path
      whitelisting; command interception partially supported.
[L3: SANDBOXED]
  └── Isolated container / OS-level sandbox (Docker, Podman, AppContainer);
      kernel namespaces, cgroups, network virtualization, zero host bleed.
[L4: NATIVE FORGE CONTROLLED]
  └── Micro-sandboxed Wasm/V8 isolate or native Forge worker;
      100% deterministic memory, tool, and instruction mediation.
```

### Authority
**Runtime Engine (`@forge/runtime-engine`) & Security Policy Authority**

### Responsibilities
- **Runtime Engine:** Discovers runtimes and assigns a certified Trust Level based on host environment capabilities.
- **Policy Engine:** Enforces that high-risk tasks (e.g., production access, arbitrary code execution) execute ONLY on runtimes satisfying the required Trust Level.
- **UI / CLI:** Explicitly displays the active Trust Level and warnings to the human operator.

### Contract
The Runtime Registry must expose:
```typescript
interface RuntimeDescriptor {
  id: string;
  name: string;
  trust_level: "L0" | "L1" | "L2" | "L3" | "L4";
  capabilities: {
    filesystem_governance: "none" | "path_jail" | "virtual_mount";
    network_governance: "unrestricted" | "allowlist" | "isolated";
    tool_interception: boolean;
    supports_cancellation: boolean;
  };
}
```

### Invariants
- `INVARIANT-003.1`: Forge shall never present an L1 runtime as fully secure or sandboxed.
- `INVARIANT-003.2`: If a project policy mandates L3 (Sandboxed), tasks shall fail or pause if only L1 runtimes are available.

### Consequences
- **Positive:** Honest security posture; enterprise-defensible; allows users to leverage existing CLIs immediately while providing a clean path to hardened containers.
- **Negative:** Increases complexity of policy checks; users must acknowledge security trade-offs for L1 runtimes.

### Rejected Alternatives
- Option C was rejected because forcing immediate Docker/container dependencies destroys the core thesis of zero-friction local developer onboarding (`forge init`).

### Affected Documents
- `00-PRODUCT-THESIS.md`: Align claims regarding external CLI governance with the L0–L4 model.
- `01-MASTER-PRD.md`: Update security requirements and runtime discovery expectations.
- `02-SYSTEM-ARCHITECTURE.md`: Include Trust Matrix in Layer 4 (Execution Layer).
- `07-RUNTIME-ENGINE.md`: Core chapter detailing L0–L4 adapters.
- `17-SECURITY-MODEL.md`: Formalize threat boundaries based on Trust Levels.

### Implementation Notes
Runtime discovery will classify native binaries found in `$PATH` (e.g. `claude`) as `L1 - TRUSTED EXTERNAL` by default unless launched within an explicit Forge Docker harness.

## AD-004 — External CLI Governance

### Status
**LOCKED**

### Context
External coding CLIs execute their own internal agentic loops. When an agent running inside Claude Code decides to read a file or execute bash, it issues system calls directly to the host OS, bypassing Forge's `Tool Execution Engine`.

### Problem
Forge cannot claim to govern tool execution, enforce least-privilege, or record immutable tool audit logs if an external CLI bypasses Forge's tool layer entirely.

### Options Considered
- **Option A (PTY Scraping & Regex Hijacking):** Intercept terminal emulator stdout/stdin to detect commands.
- **Option B (Dual Protocol Strategy: MCP Mediation & Process Virtualization — CHOSEN):** 
  - Protocol 1: Model Context Protocol (MCP) server integration where Forge exposes tools to the CLI and native CLI tools are disabled/unconfigured.
  - Protocol 2: OS-level subprocess filesystem jail (working directory mounting) with explicit boundary documentation.
- **Option C (Complete Reliance on Good Faith):** Treat external CLIs as opaque black-box workers; only verify the output artifacts at step completion.

### Decision
**Forge governs external CLIs via explicit boundary adapters.**  
1. Where supported by the external CLI (e.g., via MCP or custom tool flags), Forge injects itself as the Tool Server, routing tool calls through Forge's permission engine.  
2. Where an external CLI operates autonomously, Forge treats it as an **Opaque External Actor** (Trust Level `L1`), enforces boundary confinement via designated Git Worktrees, and relies on **Strict Pre/Post Verification** rather than real-time tool interception.  
Every Runtime Adapter must explicitly declare what it can observe, what it can control, and what remains un-intercepted.

### Authority
**Runtime Engine (`@forge/runtime-engine`)**

### Responsibilities
- **Runtime Adapters:** Must implement a standardized inspection profile:
  - `Observability`: Stdin/Stdout streaming, process metrics, token telemetry (if exposed).
  - `Controllability`: Process pause (`SIGSTOP`), graceful cancel (`SIGTERM`), hard kill (`SIGKILL`).
  - `Governance`: Declares whether tool calls are mediated or opaque.
- **Tool Execution Engine:** Executes only tools explicitly routed to it; does not claim false interception of opaque subprocesses.

### Invariants
- `INVARIANT-004.1`: Forge shall document real-time tool interception as "UNAVAILABLE" for opaque L1 CLI runtimes.
- `INVARIANT-004.2`: Un-intercepted runtimes must always undergo mandatory Verification Gate checks before work is merged.

### Consequences
- **Positive:** Architecturally sound; avoids brittle terminal scraping; leverages open standards (MCP).
- **Negative:** For opaque runtimes, Forge cannot prevent a destructive in-flight file edit; it can only catch it post-execution via Git diff rollback.

### Rejected Alternatives
- Option A was rejected because terminal screen scraping is notoriously brittle across OS versions, terminal escape sequences, and CLI updates.

### Affected Documents
- `07-RUNTIME-ENGINE.md`: Core architectural contract for CLI adapters.
- `11-TOOL-EXECUTION.md`: Boundary definition between Forge Native Tools and Opaque CLI Native Tools.
- `17-SECURITY-MODEL.md`: Risk disclosure regarding opaque external execution.

### Implementation Notes
For Claude Code and OpenCode, provide a `--mcp` configuration generator allowing Forge to serve tools over stdio/SSE where possible.

## AD-005 — Verification Authority

### Status
**LOCKED**

### Context
The core thesis asserts: *"Agent says: Done. Forge: Prove it."* However, existing documents conflated deterministic automated verification with probabilistic human/agent review.

### Problem
If an agent marks a task complete, or if a "QA Engineer" AI agent approves the code, the verification is still probabilistic and susceptible to hallucinations, syntax errors, and prompt drift.

### Options Considered
- **Option A (Agent Self-Approval):** Worker agent reports task completed; marked done.
- **Option B (QA Agent Approval):** A second agent reviews the work and signs off.
- **Option C (Dual-Layered Verification: Deterministic Engine + Semantic Review — CHOSEN):** System-level deterministic verification is mandatory and supreme; agent review is advisory/semantic.

### Decision
**Verification is strictly dual-layered with mandatory deterministic supremacy.**
- **Layer 1: Verification Engine (Deterministic & Authoritative):** Automated execution of compilers, typecheckers, linters, unit tests, integration tests, diff analyzers, and exit codes. This is managed by the system Control Plane, NOT an LLM.
- **Layer 2: Reviewer Agents (Probabilistic & Semantic):** Explores architectural alignment, style consistency, and documentation completeness.

**Task Completion Policy Matrix:**
1. `AUTOMATED`: Requires Layer 1 test suite exit code 0. Zero human or agent overrides allowed without audit flags.
2. `HUMAN_ATTESTED`: Requires explicit human operator sign-off (for UX, design, or non-compilable decisions).
3. `MIXED`: Requires Layer 1 automated pass followed by Layer 2 Reviewer Agent sign-off.

An agent saying "Done" NEVER completes a task.

### Authority
**Verification Engine (`@forge/verification-engine`)**

### Responsibilities
- **Verification Engine:**
  - Dispatches deterministic test runners in isolated test sandboxes.
  - Collects stdout, test report XML/JSON, and exit codes.
  - Issues cryptographic or structured `VerificationEvidence`.
- **Reviewer Agent:**
  - Evaluates qualitative and semantic properties; emits a `ReviewerAssessment`.
  - CANNOT override a failed Layer 1 test exit code.

### Contract
```typescript
interface VerificationEvidence {
  verification_id: string;
  task_id: string;
  layer: "DETERMINISTIC" | "SEMANTIC";
  passed: boolean;
  timestamp: string;
  checks: {
    typecheck: { passed: boolean; exit_code: number; logs: string };
    lint: { passed: boolean; exit_code: number; logs: string };
    tests: { passed: boolean; total: number; failed: number; duration_ms: number };
  };
  artifacts_verified: string[];
}
```

### Invariants
- `INVARIANT-005.1`: A non-zero exit code from Layer 1 automated checks immediately fails verification; no agent can overrule it.
- `INVARIANT-005.2`: No task with `require_verification: true` shall transition to `COMPLETED` without an authoritative `VerificationEvidence` record with `passed: true`.

### Consequences
- **Positive:** Guarantees software works; eliminates hallucinated completions; provides clear evidence logs for audit.
- **Negative:** Tasks without automated tests require manual human attestation or test creation skills upfront.

### Rejected Alternatives
- Option A was rejected as fundamentally incompatible with the Forge Wanzz product thesis.
- Option B was rejected because LLM agents frequently approve hallucinated or broken code.

### Affected Documents
- `01-MASTER-PRD.md`: Formalize Layer 1 vs Layer 2 verification expectations.
- `02-SYSTEM-ARCHITECTURE.md`: Specify `Verification Manager` in Control Plane.
- `03-AGENT-SYSTEM.md`: Clarify that agents report outputs, not verified completion.
- `05-ORCHESTRATION-ENGINE.md`: Update Verification Gate to evaluate `VerificationEvidence`.

### Implementation Notes
The Verification Engine will execute commands like `npm test`, `cargo check`, `pytest` directly via the Tool Runner under clean environment variables.

## AD-006 — Skill Disclosure

### Status
**LOCKED**

### Context
`04-SKILL-ENGINE.md` introduced a 5-tier progressive skill disclosure model. However, specifying 5 tiers in MVP introduces excessive parsing and context management overhead without validated ROI.

### Problem
Over-engineered token management models delay MVP delivery. Furthermore, treating skills as markdown files without a schema creates unpredictable prompt injections.

### Options Considered
- **Option A (Full Ingestion):** Dump the entire `SKILL.md` into the agent's context window on every turn.
- **Option B (Two-Tier Progressive Disclosure — CHOSEN):** Simplify to Tier 1 (Manifest / Metadata / 1-Line Summary) and Tier 2 (Full Procedural Workflow & Constraints).
- **Option C (Five-Tier Progressive Disclosure):** Maintain Levels 0 through 4 with AST-based dynamic chunk retrieval.

### Decision
**Forge adopts a pragmatic Two-Tier Progressive Skill Disclosure Model for MVP.**
- **Tier 1 (Index & Discovery):** Name, Description, Category, Required Tools, and Prerequisites parsed from structured YAML frontmatter. Injected into Agent Context during planning and skill selection (~50 tokens/skill).
- **Tier 2 (Operational Methodology):** Complete structured instructions, procedural workflow steps, rules, and verification criteria. Injected into the Agent Context ONLY when a task requiring that skill is actively leased.

**Security Lock:** Skills are strictly procedural instructions. **Skills MUST NOT grant permissions, modify authorization bounds, or execute tools directly.**

### Authority
**Skill Engine (`@forge/skill-engine`)**

### Responsibilities
- **Skill Engine:**
  - Parses `SKILL.md` YAML frontmatter and extracts Tier 1 metadata.
  - Validates that requested skills exist and dependencies are satisfied.
  - Injects Tier 2 content into the Task Execution Context.
  - Enforces that untrusted skills undergo security linting.

### Frontmatter Schema Contract
```yaml
---
id: "frontend-development"
name: "Frontend Development"
version: "1.0.0"
description: "Methodology for developing accessible React/TypeScript components."
tier1:
  category: "development"
  tags: ["react", "typescript", "ui"]
  required_tools: ["filesystem", "terminal"]
  compatible_roles: ["frontend_engineer", "fullstack_engineer"]
tier2:
  rules:
    - "Reuse existing component library"
    - "Verify changes via typecheck before reporting completion"
---
```

### Invariants
- `INVARIANT-006.1`: Skills are methodology assets; they cannot grant capabilities or elevate permissions.
- `INVARIANT-006.2`: An agent never receives Tier 2 skill workflows unless the task explicitly requires that skill.

### Consequences
- **Positive:** Saves up to 60% of prompt token bloat; trivial to parse via standard YAML/Markdown frontmatter libraries; clean security boundary.
- **Negative:** Granular sub-workflows within a large skill are loaded together in Tier 2 rather than streamed piece-by-piece.

### Rejected Alternatives
- Option A was rejected because passing 20 complete skill manuals exhausts the LLM context window and causes attention degradation.
- Option C was deferred to post-MVP because AST-level chunk retrieval introduces significant complexity for negligible token gains.

### Affected Documents
- `04-SKILL-ENGINE.md`: Update specification to formalize the Two-Tier model and frontmatter schema.

### Implementation Notes
Use `gray-matter` or a standard YAML frontmatter parser in Node.js/TypeScript to extract Tier 1 metadata instantly on startup.

## AD-007 — Workspace Isolation

### Status
**LOCKED**

### Context
Documents `03` and `05` celebrate parallel agent execution, but leave concurrent file modifications undefined, risking immediate file corruption and git race conditions.

### Problem
Two agents executing concurrently on the same working tree (e.g. Frontend editing `src/App.tsx` and Backend editing `src/api.ts`) will conflict during file writes, corrupt shared files like `package.json`, and cause dirty git index errors.

### Options Considered
- **Option A (Shared Directory with File-Level Locks):** Agents lock individual files before editing.
- **Option B (Git Worktree Isolation — CHOSEN):** Every concurrent writing agent receives its own dedicated Git Worktree and feature branch.
- **Option C (Strictly Sequential Execution):** Only one agent can execute at a time across the entire project.

### Decision
**Workspace isolation is governed by Access Mode. Concurrent writers MUST execute in isolated Git Worktrees.**
- **READ-ONLY Mode:** Shared project workspace is permitted.
- **SINGLE WRITER Mode:** Direct project workspace execution is permitted (isolated worktree recommended).
- **MULTIPLE CONCURRENT WRITERS Mode:** Isolated Git Worktrees are **MANDATORY**.

Each writing agent operates on a private branch (`forge/task-<task_id>`). When tasks complete verification, the Orchestrator coordinates sequential integration merges back into the primary project branch.

### Authority
**Task Engine & Runtime Workspace Manager**

### Responsibilities
- **Workspace Manager:**
  - Creates isolated git worktrees (`git worktree add .forge/worktrees/<task_id>`).
  - Passes the worktree path as the execution working directory to the Runtime Adapter.
  - Cleans up worktrees upon task completion, cancellation, or crash recovery.
- **Orchestrator:**
  - Schedules integration merges sequentially to prevent merge collisions.
  - Triggers Verification Gates on the merged result.

### Worktree Topology
```text
Project Root (main branch)
├── .git/
├── src/
└── .forge/worktrees/
    ├── task-backend-001/  (branch: forge/task-backend-001)
    └── task-frontend-002/ (branch: forge/task-frontend-002)
```

### Invariants
- `INVARIANT-007.1`: No two active tasks may have simultaneous write leases on the same workspace path.
- `INVARIANT-007.2`: Worktree merges into the main branch must be verified by automated tests before being declared permanent.

### Consequences
- **Positive:** Complete isolation; zero file lock race conditions; clean git history; failed tasks can be discarded with a simple `git worktree remove`.
- **Negative:** Requires local git repository; minor disk overhead for worktrees; merge conflict resolution logic required during integration.

### Rejected Alternatives
- Option A was rejected because file locks do not prevent build-step collisions (`node_modules`, lockfiles, build caches).
- Option C was rejected because it eliminates the massive performance advantage of parallel multi-agent development.

### Affected Documents
- `03-AGENT-SYSTEM.md`: Update Section 52 to mandate Git Worktrees for concurrent agents.
- `05-ORCHESTRATION-ENGINE.md`: Update concurrency model and workspace coordination rules.
- `07-RUNTIME-ENGINE.md`: Specify workspace directory mounting per worktree.

### Implementation Notes
The Workspace Manager must check for dirty worktrees during crash recovery and automatically purge stale worktrees older than their lease expiration.

## AD-008 — Crash Recovery & Lease Management

### Status
**LOCKED**

### Context
If the host machine reboots or the Forge process is killed (`SIGKILL`), in-flight tasks and external CLI child processes will be orphaned, and the persistent state will be desynchronized.

### Problem
Without an explicit crash recovery and execution lease protocol, Forge upon restart cannot know whether an in-flight task actually finished, is still running in an orphan process, or corrupted the repository.

### Options Considered
- **Option A (Total Reset on Crash):** Wipe in-flight state and restart the entire project from scratch.
- **Option B (Heartbeat Leases & Rehydration Protocol — CHOSEN):** Durable task execution records with time-bound leases, process group tracking, and automated startup triage.
- **Option C (Distributed Paxos/Raft Consensus):** Over-engineered distributed consensus protocol.

### Decision
**Forge implements a Durable Lease and Process Group Rehydration Protocol for crash recovery.**  
Every active execution is registered with:
`execution_id`, `task_id`, `agent_id`, `runtime_id`, `workspace_path`, `process_group_id`, `heartbeat_timestamp`, and `lease_duration_seconds` (default: 30s).

**Startup Recovery Pipeline:**
```text
FORGE STARTUP
      │
      ▼
1. Scan Active Execution Leases in SQLite
      │
      ├── Case A: Heartbeat expired & PID dead ──► Mark Task FAILED_CRASHED, clean workspace
      │
      ├── Case B: PID still alive (Orphan) ─────► Send SIGTERM/SIGKILL, clean workspace, re-queue
      │
      └── Case C: Clean checkpoint exists ──────► Rehydrate Task to READY / RESUME
```

### Authority
**Task Engine (`@forge/task-engine`) & Runtime Engine**

### Responsibilities
- **Runtime Engine:**
  - Spawns CLI processes with dedicated Process Group IDs (`setpgid`).
  - Emits heartbeats every 5 seconds to renew the task lease in SQLite.
  - Cleans up orphan process trees upon startup.
- **Task Engine:**
  - Enforces atomic state transitions using SQLite Write-Ahead Logging (WAL).
  - Automatically expires leases if heartbeats cease for $> 30\text{ seconds}$.

### Invariants
- `INVARIANT-008.1`: No task may remain indefinitely in `RUNNING` state without an active, renewed lease.
- `INVARIANT-008.2`: All background subprocesses spawned by Forge must be registered with their OS process group for clean termination.

### Consequences
- **Positive:** Immune to machine crashes and unhandled exceptions; zero zombie CLI processes consuming host CPU/RAM; state resumes gracefully.
- **Negative:** Requires periodic database write for heartbeats; 30-second delay before dead tasks are triaged and re-queued.

### Rejected Alternatives
- Option A was rejected as unacceptable for long-running software engineering projects.
- Option C was rejected as inappropriate for single-machine/local-first developer tooling.

### Affected Documents
- `05-ORCHESTRATION-ENGINE.md`: Update failure recovery and session resumption models.
- `06-TASK-ENGINE.md`: Specify lease table schema and expiration sweeps.
- `07-RUNTIME-ENGINE.md`: Implement OS process group handling and heartbeat timers.
- `16-DATABASE-SCHEMA.md`: Define `execution_leases` table.

### Implementation Notes
Use SQLite `datetime('now')` and atomic transactions: `UPDATE tasks SET status = 'FAILED' WHERE status = 'RUNNING' AND lease_expires_at < datetime('now')`.

## AD-009 — Capability Resolution

### Status
**LOCKED**

### Context
A task may demand capabilities (e.g. write filesystem, call external API), an agent may list skills, a skill may declare tool requirements, and a runtime may provide certain execution environments. Currently, there is no single gatekeeper validating if the combination is legally permitted before execution begins.

### Problem
Without an explicit, centralized capability resolution gate, permission checks are scattered across the Agent Engine, Skill Engine, and Tool Runner, creating security loopholes and privilege escalations.

### Options Considered
- **Option A (Scattered Checks):** Each subsystem checks its own local permissions ad-hoc.
- **Option B (Centralized Capability Resolver — CHOSEN):** An explicit, unified resolution pipeline that evaluates the full intersection of Task, Agent, Skill, Tool, Runtime, and Policy before issuing an `ExecutionToken`.
- **Option C (Agent Evaluates Permissions):** The agent LLM is instructed to check its own permissions.

### Decision
**Forge establishes an explicit, authoritative Capability Resolution Pipeline.**  
Before any task can dispatch to a runtime, the **Capability Resolver** must compute the intersection of requirements against governing policies.

```text
Task Requirements
      +
Agent Capabilities
      +
Skill Requirements
      +
Tool Requirements
      +
Runtime Capabilities
      +
Project Security Policy
      │
      ▼
[CAPABILITY RESOLVER]
      │
      ├── ALLOWED ──────────► Issue Execution Token
      ├── DENIED ───────────► Abort Task with Specific Capability Error
      └── APPROVAL REQUIRED ─► Transition Task to AWAITING_APPROVAL
```

**Core Principle:** `Capability Declaration ≠ Permission Grant`. A skill or runtime declaring a capability never grants itself authority; authority is granted solely by Project Security Policy.

### Authority
**Capability Resolver (`@forge/capability-resolver`) within Control Plane**

### Responsibilities
- Computes effective permissions deterministically.
- Generates human-readable explanations of missing capabilities or policy denials.
- Produces an immutable `ExecutionToken` required by the Runtime Adapter.

### Capability Resolution Matrix Example
```text
Capability Resolution Report:
Task: AUTH-BACKEND-001 | Agent: backend_engineer | Runtime: claude-code (L1)

[✓] Skill: backend-development        -> Supported & Active
[✓] Tool: filesystem.read             -> Permitted by Project Policy
[✓] Tool: filesystem.write (/src)     -> Permitted by Project Policy
[!] Tool: shell.exec (npm install)    -> Permitted (Requires Audit Log)
[✗] Tool: cloud.deploy                -> DENIED by Policy (Non-production agent)
-----------------------------------------------------------------------------
Resolution: ALLOWED WITH RESTRICTIONS
```

### Invariants
- `INVARIANT-009.1`: No runtime execution shall commence without a valid, signed `ExecutionToken` produced by the Capability Resolver.
- `INVARIANT-009.2`: The effective permission set is always the most restrictive intersection of all input policies.

### Consequences
- **Positive:** Eliminates privilege escalation; centralized security auditing; completely transparent reasons for blocked tasks.
- **Negative:** Adds a synchronous validation step prior to task dispatch.

### Rejected Alternatives
- Option A was rejected because distributed permission checks inevitably lead to security bypasses when new plugins or tools are added.
- Option C was rejected because LLMs cannot be trusted to enforce their own security boundaries.

### Affected Documents
- `02-SYSTEM-ARCHITECTURE.md`: Add Capability Resolver to Layer 2 Control Plane.
- `03-AGENT-SYSTEM.md`: Update Section 10 and 13 to conform to the Capability Resolver contract.
- `04-SKILL-ENGINE.md`: Ensure skill tool requirements pass through the Resolver.
- `11-TOOL-EXECUTION.md`: Tool runner requires `ExecutionToken`.
- `17-SECURITY-MODEL.md`: Formalize Capability Resolution as the primary ingress gate.

### Implementation Notes
The Resolver must evaluate permissions in order of precedence: `System Policy -> Project Policy -> Agent Bounds -> Task Constraints`.

## AD-010 — Task / Orchestrator Boundary

### Status
**LOCKED**

### Context
A fundamental question arising from the audit is: *Where does the Orchestrator end and the Task Engine begin?*

### Problem
Without a razor-sharp boundary, the Orchestrator bloats into a monolithic engine that handles database queries, leases, graph algorithms, state transitions, prompt engineering, and agent dispatching simultaneously.

### Options Considered
- **Option A (Merged Engine):** Combine Orchestrator and Task Engine into a single `@forge/orchestrator` module.
- **Option B (Strict Architectural Decoupling — CHOSEN):** Orchestrator is the cognitive brain; Task Engine is the deterministic nervous system and ledger.
- **Option C (Task Engine Subordinate to Orchestrator):** Task Engine is just a library embedded within the Orchestrator process.

### Decision
**The Orchestrator and Task Engine are decoupled subsystems with strictly segregated responsibilities.**

| Subsystem | Architectural Role | What it OWNS | What it MUST NOT DO |
| :--- | :--- | :--- | :--- |
| **Orchestrator** | Cognitive Coordinator | Goal Analysis, Plan Formation, Task Decomposition Proposals, Agent Matching, Replanning Strategy, Human Escalation Triggers. | Mutate database tables directly, bypass Task Engine state checks, declare completions without verification. |
| **Task Engine** | Deterministic Ledger & Queue | Task State Machine, Dependency Graphs (DAG), Concurrency Limits, Lease Locks, Task Persistence, Retry Backoff, Crash Recovery State. | Call LLM inference models, formulate project plans, select subjective agent personas. |

The Orchestrator interacts with the Task Engine exclusively via structured asynchronous commands and domain events.

### Authority
**Architectural Constitution Boundary**

### Interaction Cycle
```text
      ┌────────────────────────────────────────────────────────┐
      │                      ORCHESTRATOR                      │
      │         (Cognitive Coordination & Planning)            │
      └──────────────┬──────────────────────────▲──────────────┘
      1. ProposeTaskGraph()                     │ 3. Emit: TaskReadyEvent
      2. RequestDispatch()                      │    Emit: TaskFailedEvent
                     │                          │
      ┌──────────────▼──────────────────────────┴──────────────┐
      │                      TASK ENGINE                       │
      │       (Deterministic State Machine & Persistence)       │
      └────────────────────────────────────────────────────────┘
```

### Invariants
- `INVARIANT-010.1`: The Orchestrator contains zero direct SQL or database write queries for tasks.
- `INVARIANT-010.2`: The Task Engine contains zero LLM prompt invocations.

### Consequences
- **Positive:** Perfect separation of cognitive reasoning from deterministic state storage; allows swapping LLM planners without altering task queue mechanics; simplifies testing.
- **Negative:** Requires rigorous serialization of commands between the two subsystems.

### Rejected Alternatives
- Option A was rejected because combining cognitive reasoning with state storage results in unmaintainable spaghetti architecture that is impossible to unit-test deterministically.

### Affected Documents
- `05-ORCHESTRATION-ENGINE.md`: Cleanse all direct task management logic; convert to command dispatches.
- `06-TASK-ENGINE.md`: Frame the entire document as the definitive state, queue, and persistence engine.

# 4. GLOBAL ARCHITECTURAL INVARIANTS

Every specification and code implementation in Forge Wanzz must obey these twelve invariants:

- **`INVARIANT-001` (Single Source of Truth):** Exactly one authoritative owner exists per persistent state domain. Cross-subsystem state mutations are prohibited without passing through the owning engine.
- **`INVARIANT-002` (Coordination Decoupling):** The Orchestrator coordinates workflow intelligence; it does not own the persistent Task state, nor does it perform direct code implementation.
- **`INVARIANT-003` (Organizational Governance):** The Organization Manager alone governs team formation; the Orchestrator cannot instantiate agents unilaterally.
- **`INVARIANT-004` (Evidence Supremacy):** An agent’s self-reported "Done" claim never constitutes completion. Authoritative task completion requires deterministic evidence emitted by the Verification Engine or an explicit human override.
- **`INVARIANT-005` (Skill Permission Boundary):** Skills are strictly procedural methodologies; skills cannot grant capabilities, modify authorization matrices, or bypass security policies.
- **`INVARIANT-006` (Honest Trust Disclosures):** Every execution runtime must declare its exact Trust Level (L0–L4). Forge shall never claim security enforcement over un-sandboxed external CLI subprocesses.
- **`INVARIANT-007` (Mandatory Write Isolation):** Concurrent writing agents MUST operate in isolated Git Worktrees or isolated containers. Direct concurrent writes to a shared workspace are prohibited.
- **`INVARIANT-008` (Crash Recovery Guarantee):** All active executions must maintain durable leases and process group records in ACID storage, enabling automated cleanup and resumption upon machine restart.
- **`INVARIANT-009` (Capability Resolution Supremacy):** Capability availability does not imply authorization. No task shall execute without an explicit `ExecutionToken` issued by the Capability Resolver.
- **`INVARIANT-010` (Zero Bypass Principle):** No subsystem may bypass the validation logic, permission gates, or verification requirements of another subsystem.
- **`INVARIANT-011` (Auditability of Human Overrides):** Human operators may override policies and verification failures, but every override must be permanently recorded in the immutable audit ledger with user identity and rationale.
- **`INVARIANT-012` (Enforceable Security Boundaries):** Every advertised security guarantee must correspond to a technically enforceable boundary (OS sandbox, container, or typed parser); aspirational security claims are forbidden.
